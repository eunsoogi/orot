# AdMob 도입 사전 타당성 검토

검토 기준일: 2026-11-10. Apple, Google, 대한민국 개인정보 보호법의 공개 정책과 현재 저장소 기준선을 확인했다. 이 문서는 iOS AdMob 도입을 평가하며 SDK, 광고 계정, 광고 요청, 추가 수집을 승인하지 않는다.

## 결론

**현재 도입은 No-Go다.** 광고 위치와 대상 연령·지역, 요청 가능 비율, 선택 SDK·React Native 연결 방식, 중개 네트워크, 예상 수익을 뒷받침할 자료가 없다. Apple과 Google 정책은 광고와 건강 데이터·건강 기반 타게팅을 분리하도록 요구한다. 현재 근거로는 이 분리와 광고의 운영상 이익을 검증할 수 없다.

이 결론은 광고를 영구 배제한다는 뜻이 아니다. 광고 요청이나 SDK 설치 전에 제품 책임자가 별도 승인하고 필요한 정책·경제성·개인정보 검토를 끝내야 한다. #693은 정책 검토 결과만 제공한다. SDK 설치, 계정 생성, 광고 송출, 강제 시청, 보고서 잠금, 건강 정보 기반 타게팅은 범위에 포함되지 않는다.

## 제품 경계

#693에서 승인한 일일 보고서 흐름은 알림으로 준비 화면을 열고 사용자가 요약을 명시적으로 요청한 뒤 간결한 보고서를 보는 방식이다. 대화에서 같은 보고서를 명시적으로 요청할 수도 있다. 보고서는 저장 결과를 다시 사용하며 재생성은 명시적으로 요청해야 한다. 알림 열기, 보고서 열기, 설정 보기는 AI 실행이나 기록 전송을 일으키지 않는다. 광고는 이 흐름의 전제나 필수 잠금 해제 수단이 아니다. 치료 지원은 일일 보고서의 전제 조건이 아니다.

### 초기화 순서 초안 (미승인)

Google은 UMP 동의 정보 갱신을 매 앱 실행에서 수행하도록 안내한다. 따라서 UMP를 채택하면 광고가 보이지 않는 실행에서도 Google 동의 서비스 요청과 필요 시 개인정보 선택 화면이 생길 수 있다. 그 요청에는 건강 기록이나 화면 본문을 전달하지 않는다.

제품이 별도 Go를 내린 경우의 제안 순서는 다음과 같다.

1. 앱 실행 때 UMP 동의 정보를 갱신하고 필요한 선택 화면을 표시한다. UMP가 개인정보 옵션 진입점을 요구하면 사용자가 설정에서 다시 열 수 있게 한다.
2. 사용 지역·대상 연령·선택 화면이 광고 요청을 허용하는지 확인한다. 실제 설정이 Apple 정의의 추적 또는 IDFA 사용에 해당할 때만 ATT를 별도 검토한다.
3. 모든 제품·정책·동의 조건이 충족된 경우에만 선택한 Mobile Ads SDK와 중개 어댑터를 초기화하고 적격 화면의 광고를 요청한다. 초기화 시점의 네트워크 호출·식별자 동작은 선택할 SDK 버전과 React Native 브리지에 따라 확인한다.
4. 동의·연령·지역 상태를 확인할 수 없거나 광고를 표시할 수 없으면 광고 요청을 생략하고 앱의 핵심 기능은 그대로 제공한다.

이 순서는 Google의 동의 절차와 Orot의 개인정보 경계를 조합한 제안이며, 현재 구현 승인이나 특정 브리지 동작의 검증 결과가 아니다. 선택 SDK의 초기화 과정 자체가 어떤 데이터를 언제 어느 수신자에게 보내는지는 SDK와 브리지를 고른 뒤 공식 데이터 공개와 실제 의존성 기준으로 검토해야 한다.

## 연령, 지역, 화면과 실패 처리

- 실제 사용자 연령, 앱 대상 연령, App Store 연령 등급, 광고 요청 지역은 확인되지 않았다. Google의 콘텐츠 등급은 대상 연령을 증명하지 않는다. 배포 지역별 개인정보 동의와 미성년자 처리, AdMob 계정·앱 자격을 확인하기 전에는 광고 가능 사용자 수를 추정하지 않는다.
- 알림, 건강 기록, 복약·증상, 일일 보고서, 치료 설명, 대화, 공개 의학 검색 화면에는 광고를 배치하지 않는다. 보고서 열람·생성, 설명·출처 확인, 알림 수신을 광고 시청이나 추적 동의의 조건으로 만들지 않는다. 중립 화면에 광고를 둘 수 있는지는 앱 문맥 정책과 사용자 경험을 확인한 뒤 별도 승인해야 한다.
- 사용자가 광고를 거부했거나 요청 유형이 지역·연령상 허용되지 않거나 UMP가 요청을 허용하지 않으면 광고를 요청하지 않고 앱은 계속 사용할 수 있어야 한다. 개인 맞춤 광고 거부를 개인 맞춤 허가로 해석하지 않는다. 비개인화 광고도 UMP 상태와 현지 요건이 허용할 때만 요청한다. 상태 갱신과 광고 로드 실패는 건강 자료 전송, AI 실행, 재생성 또는 무한 재요청을 일으키지 않으며, 빈 슬롯이나 지연으로 핵심 화면을 막지 않는다.
- Google 정책은 EEA·영국·스위스 등의 동의 요건과 아동 신호를 따로 다룬다. 한국 법률도 별도로 검토해야 한다. 하나의 전역 설정으로 모든 지역·연령의 동의를 대신하지 않는다.

## 경제성

사용자 수, 광고 적격률, 요청 빈도, 광고 채움률, 노출률, 지역별 eCPM, 동의 거부 비율이 없다. 따라서 수익액이나 참여 목표를 만들지 않는다. 검토 시에는 다음 변수로 보수·기준·상향 민감도를 계산한다.

- **월 노출수:** 월 활성 사용자 × 사용자당 광고 요청 수 × 광고 요청 가능 비율 × 채움률 × 실제 표시율
- **월 총수익:** 월 노출수 × 지역·형식별 eCPM ÷ 1,000
- **월 순기여:** 월 총수익 - 개발·업데이트·동의·정책검토·QA·지원 운영비

광고 요청 가능 비율에는 연령·지역·법적 자격, 동의 상태, 광고가 없는 화면과 정책상 제외되는 흐름을 반영한다. 신규 분석 데이터나 건강 기록으로 사용자를 분류해 이 값을 구하지 않는다. 실제 유사 서비스·지역·형식의 확인 가능한 단가와 운영 비용이 확보되기 전에는 경제성 판단을 보류한다.

## 재검토 조건과 구현 경계

별도 구현 이슈를 열기 전에 제품 책임자의 명시적 Go, 사용 연령·지역 결정, 광고 없는 핵심 경로, 화면 배치, 확인된 경제성 가정이 필요하다. 선택 SDK·브리지·중개 파트너 버전의 데이터 흐름, 초기화 순서와 수신자를 확인하고 Google 정책 적격성·지역별 UMP/ATT 동의·실패 처리를 검증해야 한다. App Store 개인정보 공개와 포함된 모든 SDK manifest를 실제 수집에 맞게 갱신하고, 건강 자료와 광고 요청 사이에 코드 수준의 전달 경로가 없음을 별도 검증해야 한다.

이 조건은 현재 도입 승인이 아니다. 각 조건과 실제 배포 정책이 확인되기 전까지 광고 SDK·UMP/ATT 화면·광고 계정·광고 노출을 추가하지 않는다. 새 SDK 선택과 런타임 격리 검증은 별도 승인된 구현 범위로 남긴다.
